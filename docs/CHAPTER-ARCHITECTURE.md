# 章节留档架构(CHAPTER)

> 器灵工作流 v0.4.0 新增功能:**章节化 API + 流程留档**。
> 文档即代码:既是项目开发留档,也是 API 文档。

---

## 一、设计理念

### 为什么不以任务留档

| 任务留档 | 章节留档 |
|----------|----------|
| 一个端点 = 一个任务,20 端点 = 20 份文档 | 一个 ql 循环 = 一章节,与交付对齐 |
| 任务粒度过细,碎片化 | 章节粒度适中,聚合 |
| 对外用户看不懂内部任务 | 对外用户看章节即可 |
| 流程不连贯(分散在多个任务) | 流程完整(讨论→构建→交付) |
| 难以维护,容易过期 | 自动生成,与代码同步 |

### API 驱动的核心

本插件是 **API 驱动开发**:
- 讨论阶段产出 OpenAPI(机器可读契约)
- 构建阶段填充 OpenAPI 实现
- 验证阶段对照 OpenAPI 验收
- 交付阶段 OpenAPI + 流程 = 章节文档

**OpenAPI 是单一可信源,章节文档是它的"渲染快照"。**

## 二、产出布局

```
.qiling/                                    # 章节留档根目录(项目本地)
├── README.md                               # 章节索引(门户型文档)
└── docs/
    └── chapters/
        ├── chapter-01-user-center.md       # 第 1 章:用户中心
        ├── chapter-02-order-center.md      # 第 2 章:订单中心
        ├── chapter-03-payment.md           # 第 3 章:支付集成
        ├── chapter-NN-*.md                 # ...更多章节
        └── .diffs/                         # 章节间差异(可选)
```

**为什么放 `.qiling/` 而不是仓库根:**
- 项目本地目录,与运行时数据(`.planning/`)隔离
- 与 `.git/`(版本控制)、`node_modules/`(依赖)区分
- 用户进入项目一眼能看到三个目录:`.git/`(版本)、`.planning/`(工作流数据)、`.qiling/`(对外文档)

## 三、章节文件结构

每个 `chapter-NN-*.md` 包含 5 节:

| 节 | 内容 | 数据来源 |
|----|------|----------|
| **§一** | 本章节交付的 API(详细) | OpenAPI 全部内容 |
| **§二** | 本章节开发流程留档 | build/skeleton/fill/verification 报告 + git log |
| **§三** | 与上一章节的对比 | OpenAPI diff(自动) |
| **§四** | 关联文档链接 | STATE.md、openapi.yaml、其他章节 |
| **§五** | 变更日志 | 本章节的修改历史(只读快照,基本只有"自动生成"一行) |

---

## 四、§一 详细 API 文档

**包含元素:**
1. 端点清单表(方法、路径、摘要、认证、速率限制)
2. 端点详情(每个端点:请求参数、响应、错误码、**使用示例**)
3. 数据模型(每个 schema:字段表 + schema YAML + 示例)
4. 错误码参考表(HTTP + code + 含义 + 触发时机)

**使用示例覆盖:**
- `curl`(命令行)
- TypeScript `fetch`
- Python `requests`
(模板可扩展更多语言)

**为什么含示例:**
- API 文档最大的痛点是"知道接口但不知道怎么调用"
- 自动生成示例让 API 文档**可直接运行**,降低接入门槛

---

## 五、§二 开发流程留档

**包含:**
1. **阶段时序图**(mermaid timeline)
2. 讨论产出(openapi.yaml + event-flow.md 摘要)
4. 验证报告(契约符合度、流程符合度、测试统计)
5. **Git 历史摘要**(本章节的所有 commit,带 worker 归属)
6. 关键指标(协调器上下文使用、波次冲突率、覆盖率)

**为什么需要这一节:**
- 对维护者:快速理解"这章代码是怎么写出来的"
- 对升级者:看 git 历史知道改动分布
- 对未来 AI 助手:上下文恢复,知道"为什么这样设计"

## 六、§三 变更对比

| 对比维度 | 用途 |
|----------|------|
| 新增 API | 升级指南的"我需要接入这些" |
| 修改 API | 是否破坏性变更 |

| 迁移指南 | 从旧版本升级的具体步骤 |

**首章节无对比,§三 显示"无上一章节"。**

## 七、触发时机

```
ql-discuss(讨论)         # 产出 OpenAPI
    ↓
ql-build(波次并行构建)   # 产出 skeleton + fill + verification
    ↓
ql-ship(交付)            # 推送 PR
    ↓
ql-chapter(章节留档)     # 自动调用,生成 .qiling/docs/
```

**默认:** `/ql-ship` 完成后自动调用 `/ql-chapter`。

**手动触发:**
- `/ql-chapter --preview`:预览,不写文件
- `/ql-chapter --regenerate-all`:模板变更后批量重生

## 十、给用户的实践建议

### 何时查看 `.qiling/docs/`

- **作为新成员入门:** 看 `.qiling/docs/README.md` 索引,了解项目能力
- **作为 API 使用者:** 进入对应章节的 §一,直接复制使用示例
- **作为维护者:** 进入对应章节的 §二 + git 历史,理解代码演进
- **作为升级者:** 对比相邻章节的 §三,看变更与迁移

### 何时修改章节文档

**永远不要**——这是只读快照。
若内容有误,正确做法是:
1. 修改 `.planning/context/openapi.yaml`(源头)
2. 重跑 `/ql-discuss` 或直接 `/ql-build`(取决于修改幅度)
3. 重跑 `/ql-ship`(自动重新生成章节)

## 十二、章节留档 vs 任务留档(等价性论证)

> **核心论点:** 章节粒度是任务粒度的**等价替代**,而非低配版。"完整的任务留档能力"已经在章节文档中**全部承载**——不需要额外维护 `.planning/tasks.md` 或在 `STATE.md` 加任务清单节。

### 12.1 "完整任务留档能力"的字面拆解

一般"任务留档系统"承诺的字段:

| 字段 | 含义 | 章节留档对应位置 |
|------|------|------------------|
| 任务列表 | 列出所有端点/事件 | §一.1 端点清单(从 OpenAPI paths 提取) |
| 任务状态 | pending / in-progress / done | 章节 frontmatter `status: shipped` + §二.2 阶段时序 |
| 进度百分比 | 已完成 / 总数 | §一 端点表(每行都是已完成的端点)+ §一.4 错误码表 |
| 负责人 / Owner | 谁实现的 | §二.6 Git 历史(每个 commit 标注 wave / worker) |
| ETA / 计划完成时间 | 何时完成 | §二.1 阶段时序图 + `generated_at` 时间戳 |
| 阻塞 / 风险 | 当前卡点 | §一.4 错误码 + §二.7 关键指标 + 已知问题 |
| 完成时间 | 实际交付 | 章节 frontmatter `generated_at` + GitHub PR 链接 |
| 任务依赖 | A 依赖 B | §一.1 端点表 + §三 与上一章节对比 |
| 任务评论 / 备注 | 实现说明 | §二.3 / §二.4 报告摘要(从 skeleton/fill/verification 提取) |
| 子任务 | 端点的步骤拆分 | §二.3 构建阶段产出(骨架→填充→验证 子阶段) |

**10 项任务留档字段,章节文档全部覆盖。**

### 12.2 字面对照表(章节留档如何"等价"于任务留档)

| 任务系统字段 | 章节留档承载位置 | 等价强度 |
|-------------|-----------------|----------|
| 任务 ID | 章节 frontmatter `chapter_id` | ✅ 直接映射 |
| 任务标题 | 章节 frontmatter `title` | ✅ 直接映射 |
| 任务状态 | frontmatter `status` ∈ {shipped, shipped_with_gaps, shipped_failed} | ✅ 等价(且更准确:反映合并后状态) |
| 任务列表 | §一.1 端点清单表 + §一.3 数据模型表 | ✅ 一行 = 一个任务 |
| 子任务 | §二.3 骨架/填充/验证三子阶段 | ✅ 三层子任务 |
| 负责人 | §二.6 Git 历史(每 commit 标 wave-N-worker-M) | ✅ 比"人"更精确(每个 worker 独立上下文) |
| ETA | §二.1 阶段时序图 + frontmatter `generated_at` | ✅ 阶段时序即甘特图 |
| 阻塞 / 风险 | §一.4 错误码 + §二.7 关键指标 | ✅ 错误码即风险清单 |
| 依赖 | §三 与上一章节对比 + §一.1 端点表 | ✅ schema 引用即依赖图 |
| 备注 | §二.3 / §二.4 / §二.5 报告摘要 | ✅ 文字注释 |

### 12.3 为什么章节粒度比任务粒度更适合 API 驱动

**任务粒度的三大问题:**

1. **碎片化** — 20 个端点 = 20 个独立任务条目,无法形成对外文档;用户看到 20 行 checkbox 不知从何读起
2. **过度细节** — 任务级别字段(负责人姓名、精确 ETA 小时)对**API 用户**无价值,只有项目管理需要
3. **维护成本高** — 双簿记:任务系统要写一次,代码要写一次,文档再写一次,三者容易脱钩

**章节粒度的三大优势:**

1. **聚合** — 一个章节 = 一个完整交付(讨论→构建→交付),聚合了 N 个端点任务的成果
2. **对外可发布** — `.qiling/docs/README.md` 是门户型文档,直接给 API 使用者看,不需要 GSD 内部任务列表
3. **单一可信源** — 章节文档**只由 OpenAPI + build 报告生成**,手动修改无效——不存在"双簿记"问题

### 12.4 何时才需要任务级清单

| 场景 | 章节留档足够? |
|------|----------------|
| 对外发布 API 文档 | ✅ 章节就是文档 |
| 项目维护者看进度 | ✅ 章节 frontmatter + 时序图足够 |
| 跨会话续作 | ✅ `current_phase` + 章节 ID 足够 |
| 高层管理周报 | ✅ 索引 README 列出所有章节 + 状态 |
| 单端点级别负责人 | ⚠️ 章节粒度看不到个人,但 Git history 已记录 worker ID |
| 单端点 ETA 跟踪 | ❌ 若必须精确到小时,需 `.planning/tasks.md` |

**结论:对于"以章节作为项目开发文档"这一目标,不需要任务粒度。**

### 12.5 与 GSD 的对比(为何器灵弃任务列表)

| 维度 | GSD(任务列表) | 器灵(章节留档) |
|------|---------------|----------------|
| 最小留档单位 | 任务(端点/事件) | 章节(ql 循环) |
| 文档与代码同步 | 手动同步 | 自动从 OpenAPI 渲染 |
| 对外可读性 | 仅内部 | 公开 API 文档 |
| 双簿记 | 有(任务 + 代码 + 文档) | 无(单一可信源) |
| 跨会话恢复 | 看 STATE.md | 看 STATE.md + 章节 frontmatter |
| 适合场景 | 复杂项目协同 | API 驱动开发 |
