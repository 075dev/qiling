# 章节留档架构(CHAPTER)

> 器灵工作流 v0.4.0 新增功能:**章节化 API + 流程留档**。
> 文档即代码:既是项目开发留档,也是 API 文档。

---

## 一、设计理念

### 为什么不以任务留档

| 任务留档 | 章节留档 |
|----------|----------|
| 一个端点 = 一个任务,20 端点 = 20 份文档 | 一个 ql 循环 = 一章节,与交付对齐 |
| 任务粒度过细,碎片化 | 章节粒度适中,聚合 |
| 对外用户看不懂内部任务 | 对外用户看章节即可 |
| 流程不连贯(分散在多个任务) | 流程完整(讨论→构建→交付) |
| 难以维护,容易过期 | 自动生成,与代码同步 |

### API 驱动的核心

本插件是 **API 驱动开发**:
- 讨论阶段产出 OpenAPI(机器可读契约)
- 构建阶段填充 OpenAPI 实现
- 验证阶段对照 OpenAPI 验收
- 交付阶段 OpenAPI + 流程 = 章节文档

**OpenAPI 是单一可信源,章节文档是它的"渲染快照"。**

## 二、产出布局

```
.qiling/                                    # 章节留档根目录(项目本地)
├── README.md                               # 章节索引(门户型文档)
└── docs/
    └── chapters/
        ├── chapter-01-user-center.md       # 第 1 章:用户中心
        ├── chapter-02-order-center.md      # 第 2 章:订单中心
        ├── chapter-03-payment.md           # 第 3 章:支付集成
        ├── chapter-NN-*.md                 # ...更多章节
        └── .diffs/                         # 章节间差异(可选)
```

**为什么放 `.qiling/` 而不是仓库根:**
- 项目本地目录,与运行时数据(`.planning/`)隔离
- 与 `.git/`(版本控制)、`node_modules/`(依赖)区分
- 用户进入项目一眼能看到三个目录:`.git/`(版本)、`.planning/`(工作流数据)、`.qiling/`(对外文档)

## 三、章节文件结构

每个 `chapter-NN-*.md` 包含 5 节:

| 节 | 内容 | 数据来源 |
|----|------|----------|
| **§一** | 本章节交付的 API(详细) | OpenAPI 全部内容 |
| **§二** | 本章节开发流程留档 | build/skeleton/fill/verification 报告 + git log |
| **§三** | 与上一章节的对比 | OpenAPI diff(自动) |
| **§四** | 关联文档链接 | STATE.md、openapi.yaml、其他章节 |
| **§五** | 变更日志 | 本章节的修改历史(只读快照,基本只有"自动生成"一行) |

---

## 四、§一 详细 API 文档

**包含元素:**
1. 端点清单表(方法、路径、摘要、认证、速率限制)
2. 端点详情(每个端点:请求参数、响应、错误码、**使用示例**)
3. 数据模型(每个 schema:字段表 + schema YAML + 示例)
4. 错误码参考表(HTTP + code + 含义 + 触发时机)

**使用示例覆盖:**
- `curl`(命令行)
- TypeScript `fetch`
- Python `requests`
(模板可扩展更多语言)

**为什么含示例:**
- API 文档最大的痛点是"知道接口但不知道怎么调用"
- 自动生成示例让 API 文档**可直接运行**,降低接入门槛

---

## 五、§二 开发流程留档

**包含:**
1. **阶段时序图**(mermaid timeline)
2. 讨论产出(openapi.yaml + event-flow.md 摘要)
4. 验证报告(契约符合度、流程符合度、测试统计)
5. **Git 历史摘要**(本章节的所有 commit,带 worker 归属)
6. 关键指标(协调器上下文使用、波次冲突率、覆盖率)

**为什么需要这一节:**
- 对维护者:快速理解"这章代码是怎么写出来的"
- 对升级者:看 git 历史知道改动分布
- 对未来 AI 助手:上下文恢复,知道"为什么这样设计"

## 六、§三 变更对比

| 对比维度 | 用途 |
|----------|------|
| 新增 API | 升级指南的"我需要接入这些" |
| 修改 API | 是否破坏性变更 |
| 删除 API | 是否需要迁移 |
| 不兼容变更 | **明确标注**,版本号需 major bump |
| 迁移指南 | 从旧版本升级的具体步骤 |

**首章节无对比,§三 显示"无上一章节"。**

## 七、触发时机

```
ql-discuss(讨论)         # 产出 OpenAPI
    ↓
ql-build(波次并行构建)   # 产出 skeleton + fill + verification
    ↓
ql-ship(交付)            # 推送 PR
    ↓
ql-chapter(章节留档)     # 自动调用,生成 .qiling/docs/
```

**默认:** `/ql-ship` 完成后自动调用 `/ql-chapter`。

**手动触发:**
- `/ql-chapter --preview`:预览,不写文件
- `/ql-chapter --regenerate-all`:模板变更后批量重生

## 九、与 docs/ 的区别

| 维度 | docs/(本目录) | .qiling/docs/(章节留档) |
|------|----------------|--------------------------|
| 内容 | 插件自身文档 | 项目开发文档 |
| 维护者 | 插件开发者 | 器灵工作流自动 |
| 变更频率 | 偶尔 | 每次 ship |
| 受众 | 插件使用者 | 项目使用者 + 维护者 |
| 版本控制 | 与插件同步 | 与项目同步 |

**两者并存,职责分明。**

## 十、给用户的实践建议

### 何时查看 `.qiling/docs/`

- **作为新成员入门:** 看 `.qiling/docs/README.md` 索引,了解项目能力
- **作为 API 使用者:** 进入对应章节的 §一,直接复制使用示例
- **作为维护者:** 进入对应章节的 §二 + git 历史,理解代码演进
- **作为升级者:** 对比相邻章节的 §三,看变更与迁移

### 何时修改章节文档

**永远不要**——这是只读快照。
若内容有误,正确做法是:
1. 修改 `.planning/context/openapi.yaml`(源头)
2. 重跑 `/ql-discuss` 或直接 `/ql-build`(取决于修改幅度)
3. 重跑 `/ql-ship`(自动重新生成章节)
