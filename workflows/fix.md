<purpose>
**修 Bug 指导 —— 复现优先,根因唯一。**

**铁律:未输出根因结论之前,禁止产生任何修复 diff。** 越是赶时间、越是"看起来很明显",越要执行本条——症状修复即失败。

Bug 修复最容易犯的两个错误:**没复现就改**(改完不知道修没修对)和**没找到根因就打补丁**(同样的 bug 换个地方再犯)。本工作流用门控强制顺序:复现 → 根因 → 最小修复 → 回归验证。
</purpose>

<available_agent_types>
- **ql-reviewer** —— 修复触及核心逻辑或多处修改时的轻量独立评审(可选,`--no-review` 跳过)
- **ql-builder-coordinator** —— 大修(≥ 3 文件)时派发定向修复
</available_agent_types>

<process>

## 步骤 0: 勘察(Orient)

**先收集,再动手。** 从任务描述与仓库中收集:

```bash
# 近期提交(近期提交常引入 bug)
git log --oneline -10

# 报错涉及的关键词在代码中的位置
grep -rn "<报错关键词>" --include="*.ts" --include="*.js" src/ 2>/dev/null | head -20
```

- 报错信息原文、复现步骤(用户提供或日志推断)
- 涉及的代码文件与调用链
- 该代码的近期变更(`git log -p <file>`)
- `.planning/bugfix/` 编号:现有最大 NNN + 1

**行为变更前提:** 若 bug 涉及契约偏差(实际行为 ≠ openapi.yaml),先确认契约与实现哪个是对的——这决定修代码还是修契约。

## 步骤 1: 复现(硬门控)

建立**可复现路径**并确认当前失败:

- 能写成测试的 → 写一个失败测试(放正确目录,命名体现 bug)
- 不能写成测试的 → 固化为一组命令/脚本,记录失败输出

```
复现成功标准:稳定看到 bug 的失败表现,并保存失败证据(输出/截图/日志摘录)。
无法复现 → 停下,用 AskUserQuestion 向用户要更多信息;Never-Ask 时列出已排除的假设,请求补充材料后中止,不盲改。
```

**复现必须优先固化为自动化失败测试**——手点复现只用于定位,最后必须落成测试。两条判废规则:

- 测试**立即通过** = 复现无效(你在测已有行为),修测试直到它真实失败
- 报错**而非断言失败** = 复现不干净,修到能正确失败为止

**绝不跳过本步直接改代码。**

## 步骤 2: 根因分析

**本步骤结束前,工作区不得出现任何修复 diff。** 从四个来源交叉定位根因:

| 来源 | 用法 |
|------|------|
| 报错/日志 | 从第一个异常点沿调用链向上游找 |
| `git blame` / `git log -p` | 该行为何时引入?伴随哪个功能? |
| 边界插桩 | 在怀疑路径打日志/断点,缩小范围 |
| 契约对照 | 实现与 openapi.yaml/event-flow.md 的偏差 |

**模式分析:** 找同库中类似的正常实现,完整阅读,穷举工作代码与损坏代码之间的每一处差异——不预设"这个无关"。

**根因判定标准:** "修复它之后,此类问题不再出现"的最低层原因。症状(`列表页报 500`)不是根因(`分页参数为 0 时 SQL OFFSET 为负`)。输出**一句话假设**:"X 是根因,因为 Y"——说不清就还没找到。

## 步骤 3: 最小修复

1. **回归测试先失败** —— 针对根因写回归测试,确认它以"bug 的方式"失败
2. **最小修复** —— 只改根因相关的代码;发现顺手可改进处,记录到报告"遗留"段,不顺带改
3. **测试通过** —— 回归测试转绿;原有相关测试不破

**两次即停:** 连续两次修复未让复现路径转绿 → **停止打补丁**,回到步骤 2 重新推导根因(换来源交叉验证,单变量验证假设:一次只改一处)。连续三次失败往往说明**不是假设错,而是设计错**——明确向用户提示升级为设计层讨论(`/ql-design` 重审契约,或 `/ql-add` 重新规划该处)。仍无头绪 → 写 bugfix 报告(状态 `blocked`)并报告已排除的假设。

## 危险信号(出现即回炉)

| 危险信号 | 正确动作 |
|----------|----------|
| "先快速修一下,回头再查根因" | 回到步骤 2 |
| "95% 是 X 的原因,直接改" | 先说清"为什么是 X",说不清就不算 |
| 修 A 处后同样症状出现在 B 处 | 不是两个 bug,是没找到根因 |
| "顺手把这里也重构一下" | 记入报告"遗留"段,本次不动(no 搭车改进) |
| 修完不敢跑全量测试 | 说明修复信心来自侥幸,回到步骤 4 |
| 改测试让它通过 | 修的是代码,不是测试(除非契约本身错了) |

## 步骤 4: 回归验证(fresh evidence)

```bash
# 全量验证(从项目实际目录跑)
npm test        # 或仓库实际测试命令
npm run build   # 或仓库实际构建命令
```

- 每条命令记录一行:命令 + PASS/FAIL/PRE-EXISTING
- **同类检查:** `grep` 搜索同模式的代码(同样的边界写法/同样的调用),确认无潜伏同类 bug;有则一并修或记录
- 亲自读输出,不以记忆或子代理转述为准

## 步骤 5: 独立评审(可选)

**触发:** 修复触及核心逻辑、跨 ≥ 3 文件、或用户未加 `--no-review`。

派发 `ql-reviewer`(全新上下文),提供:bug 描述、根因结论、`git diff`、回归验证摘要。评审聚焦:

1. 修复是否真正解决根因(而非掩盖症状)
2. 回归测试是否锁定该 bug(改回旧代码会红)
3. 是否引入新问题

verdict = `criticals_found` → 按评审意见回到步骤 3;两轮不收敛 → 报告僵局。

## 步骤 6: 留档

1. 写 `.planning/bugfix/NNN-<slug>.md`(用 `@../templates/bugfix-report.md`)
2. 若 `.qiling/docs/` 已存在:向当前章节(或 bug 涉及端点所在章节)的 **§五 变更日志**追加一行:`- [YYYY-MM-DD] fix: <一句话>(bugfix-NNN)`
3. 若 `.planning/STATE.md` 存在:在"已知阻塞"或决策段追加 bugfix 记录(**不推进 `current_phase`**)

## 步骤 7: 报告

```
✅ Bug 修复完成(bugfix-NNN)

复现路径:<测试名或命令>
根因:<一句话>
修复:<文件:行,一句话>
回归验证:测试 N/N,构建 PASS
同类检查:<无同类 / 修复 M 处 / 记录 K 处>
评审:<approved / skipped / criticals 已解决>

下一步:直接使用;若修复暴露设计缺口,转 /ql-add
```

</process>
