# 章节索引模板

> **用途:** `.qiling/docs/README.md`(章节索引)
> **作用:** 用户访问项目时的"门户型文档"——项目的**产品说明书**首页
> **维护:** 由 `scripts/docsmap.mjs`(/ql-scan)与 `/ql-doc` 流程共同增量更新,两者产出格式**完全一致**

---

## 文件模板

```markdown
# [项目名] · 文档树(产品说明书)

> 本目录由器灵工作流自动维护,是本项目的**门户型文档**。
> 章节文件 = `/ql-scan`(项目初始化)+ `/ql-doc`(构建交付后)共同产出,两者结构完全一致。
> **项目定位:** [package.json description 或一句话概括——说明书第一段:这是什么、解决什么问题]

## 如何阅读(按角色 × 意图)

| 你想做什么 | 去哪里看 |
|------------|----------|
| 快速了解项目是什么、能做什么 | 本页"项目元信息" + 初始化章节的 §一/§二 |
| 查某个 API 怎么调用 | 章节的 §一(端点表 + 示例);初始化章节的 §一.2 路由清单 |
| 了解代码结构与启动方式 | 初始化章节的 §二(技术栈/目录树/启动流程) |
| 知道某次交付改了什么、怎么迁移 | 对应章节的 §三(与上一章节对比) |
| 给项目加新功能,代码放哪 | 初始化章节的 §二.5"新代码放哪" + `/ql-design` |

| 字段 | 值 |

> **新鲜度提示:** 若当前 HEAD 已落后文档基线 commit 较多(可用 `git log --oneline <基线>..HEAD` 查看),说明代码已演进、文档可能过期——项目结构大改后运行 `/ql-scan --force` 重扫。

## 严谨性约定(本文档树的所有章节共同遵守)

1. **证据锚点** —— 能力清单每条附 `文件:行号`;ql-doc 章节的 API 以 `openapi.yaml` 为单一可信源
2. **未检出显式声明** —— 扫描不到的内容写"未检出(Not detected)"+ 原因,绝不留空、绝不编造
3. **推断必须标注** —— 目录职责、框架用途等推断内容一律带"(推断)"标记
4. **不画假图** —— mermaid 图只引用真实检测值(入口文件、脚本名),检不出就不画
5. **只读快照** —— 章节文档不要手改;变更走源头(openapi.yaml / 代码)后重新生成

---

**生成:** 器灵工作流 v[版本],任何章节文件变化时增量更新

**维护原则:** 本文件自动维护,**不要手改**
```

<purpose>

**索引文件**(`README.md`)是**门面文档**,定位是项目的"产品说明书"首页:

- **导读先行** —— 开头一句话定位(是什么、解决什么问题),再给"按角色 × 意图"的路由表,读者 10 秒内找到入口
- **章节列表** —— 状态/来源/能力计数一目了然,链接直达
- **能力总览** —— 跨章节汇总(端点/事件/错误码/数据模型),去重后形成全项目 API 地图
- **新鲜度** —— 基线 commit + 过期提示,读者可判断文档可信度
- **严谨性约定** —— 把证据锚点 / Not detected / 推断标注 / 不画假图写成显式契约,所有章节统一遵守

**与 `/ql-scan` 的关系:** `scripts/docsmap.mjs` 渲染的索引与本模板**逐节对齐**(能力总览中 scan 章节无 OpenAPI 数据的子表,由 `/ql-doc` 章节累积后填充)。两命令产出不得格式分裂。

</purpose>
