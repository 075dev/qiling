# 决策轨迹(Decision Trace)

> 设计决策的留痕账本:**选了什么、为什么、否掉了什么、代价是什么**。
> 消费方:/ql-build 的协调器与 worker(理解设计意图,契约没规定的细节按决策精神补齐)、
> /ql-fix 的根因判定(行为异常先查"是缺陷还是设计如此")、独立评审(评审设计参照)。

## 决策记录(append-only)

| # | 决策(decision) | 理由(reason) | 否掉的备选(alternatives) | 代价(tradeoff) | 状态 | 日期 |
|---|----------------|---------------|--------------------------|-----------------|------|------|
| D1 | [一句话:选了什么] | [为什么它比备选更贴合本项目的具体约束] | [真实被否的命名选项,如"自研错误格式;直接复用框架默认"] | [该选择真实损失了什么,如"错误响应多一跳映射"] | active | [日期] |
| D2 | | | | | superseded(取代者:D5) | |
| D5 | [一句话] | | | | active(取代 D2) | |

## 质量标准(三条硬标准,不达标不算决策轨迹)

1. **reason 绑定具体细节** —— 必须引用本次讨论/本项目的事实(既有 schema、用户场景、宪法条文),不写"更优雅""业界最佳实践"这类万金油
2. **alternatives 是真选项** —— 必须是讨论中真实考虑过的命名方案,不是故意立起来打倒的稻草人
3. **tradeoff 是真代价** —— 写清这个选择"更差在哪"(性能、灵活性、迁移成本),不写审美托词("不够简洁")

## 不登记(显式排除)

- 用户显式指令 → 记 openapi.yaml 的 `## Clarifications`(那是 Q→A 记录,不是决策分析)
- 宪法已有条文 → 引用宪法编号即可,不重复成文
- 显然无争议的实现细节(文件命名、函数拆分)→ 不 trace,防账本被琐碎淹没

## 追加纪律

- 编号单调递增,不复用、不重排
- 推翻旧决策:旧行 status 改 `superseded(取代者:D-N)`,新行首列写 `取代 D-M`——**旧决策的分析过程是历史事实,删了它,后来者会重蹈覆辙**
- /ql-add 的每条新决策与本账本既有条目冲突时,必须走"取代"流程,**不允许静默另起炉灶**

<purpose>

决策轨迹解决一个跨上下文的失忆问题:**契约写的是"结论",决策轨迹写的是"论证过程"**。

**问题它解决:** /ql-design 聊完后,openapi.yaml 只留下结论("错误码用 BUSINESS_ERROR"),但"为什么不用框架默认错误格式、当时否掉了什么"只存在于当轮聊天里。下游三方全是瞎子——worker(全新 200k 上下文)在契约没规定的细节上只能瞎猜;独立评审发现实现与契约不符时,分不清"实现错了"还是"契约滞后于决策";/ql-add 补契约时可能默默推翻既有决策,连"推翻"这个动作本身都无人知晓。

**解决方案:** 讨论中每个非显然选择即时落一行账(decision / reason / alternatives / tradeoff),append-only,处处引用。

**关键原则:**

1. **结论与论证分离存储** —— 契约保持机器可执行的纯结论;论证过程进 decisions.md,互不污染
2. **append-only,取代留痕** —— 与 review.md 处置账本同一纪律:只能追加,推翻必须显式登记"取代 D-N"
3. **质量三标准** —— reason 绑定本项目细节、alternatives 是真选项、tradeoff 是真代价;不达标的 trace 比没有更糟(制造"考虑过了"的假象)
4. **典型规模** —— 一轮讨论 5~10 条为宜;一条没有 = 大概率全走了默认假设而未做真实选择;几十条 = 在 trace 琐碎细节

</purpose>
